# I AM BISON — v0.2 M2 ENCOUNTER / ROUTE Specification

## 1. Purpose

v0.2 M2 turns the current prototype from a **fixed obstacle demo** into a game that can keep producing meaningful route decisions.

The current build already has the important moment-to-moment systems:

- continuous forward movement
- herd steering
- herd-size turn penalty
- delayed turn propagation
- separation / loss
- wild-bison recruitment
- rocks
- breakable fences
- rivers
- score / game over / retry
- camera and impact / recruitment feel

The missing layer is now **encounter structure**.

At the moment, wild bison and obstacles exist only at a small set of fixed coordinates. Once the player passes them, the run stops producing new decisions.

The goal of this milestone is:

> Make the player repeatedly choose between safety, herd growth, and difficult routes while the run continues.

This milestone should answer:

> Does the existing herd-control system become substantially more interesting when the world continuously presents readable choices?

---

## 2. Core design principle

The game should repeatedly create decisions such as:

- safe route vs more recruitable bison
- short route vs easier route
- enough herd to break through vs detour
- cross disruptive terrain for a reward vs stay safe
- preserve a large herd vs risk losing some to gain even more

The player should rarely feel that they are merely driving through empty space.

The intended loop is:

1. see an upcoming situation
2. read the available routes
3. choose a route
4. execute the turn
5. gain or lose herd members
6. immediately face the next decision

The encounter system exists to support the existing herd mechanics, not replace them.

---

## 3. Scope rule

Implement **route / encounter generation only**.

Do not add:

- MOMENTUM / STAMPEDE meter
- power-ups
- predators
- enemies
- cars
- buildings
- new obstacle types
- new game modes
- progression / unlocks
- currency
- permanent upgrades
- final art
- final audio
- story
- save data
- online systems
- leader abilities

Do not redesign the herd simulation unless a small compatibility fix is necessary.

Do not change the current leader-crash rule in this milestone.

---

## 4. World progression model

For this milestone, the course has a clear primary direction:

> forward = negative world Y

The player may move left or right to choose routes, but content generation assumes the run generally advances upward through the world.

This is deliberate.

Do not implement arbitrary rotated procedural chunks yet. Axis-aligned content keeps the existing Rock, Fence, and River collision code simple and lets us evaluate route design before building a more general generator.

### Progress value

Track an internal course progression value based on forward travel:

~~~ts
courseProgress = Math.max(0, spawnY - leaderY)
~~~

This value is used for:

- deciding when new encounter chunks should exist
- selecting difficulty bands
- cleanup behind the player

It does **not** have to replace the current displayed DISTANCE score.

The current score behavior may remain unchanged for this milestone.

---

## 5. Encounter chunks

Replace the current one-time fixed world layout with reusable hand-authored encounter templates.

An encounter chunk is a local arrangement of existing gameplay objects.

Each template can contain:

- wild bison groups
- rocks
- fences
- rivers

Each template is authored relative to a chunk anchor.

Suggested conceptual shape:

~~~ts
interface EncounterTemplate {
  id: string;
  minProgress: number;
  maxProgress?: number;
  weight: number;
  length: number;

  wildGroups: LocalWildGroup[];
  rocks: LocalPoint[];
  fences: LocalFence[];
  rivers: LocalRiver[];
}
~~~

The exact type names may differ.

The important rule is:

> templates are data, not separate scene-specific hardcoded spawning functions.

A template should be easy to inspect and tune in one file.

---

## 6. Hand-authored first encounter set

Create approximately **6 encounter templates** for M2.

They should be deliberately different.

### A. Recruit Lure

Purpose:

- teach that leaving the safest line can increase herd size

Layout concept:

- obvious safe lane
- 3–5 wild bison off to one side
- one or two rocks make the reward lane require a deliberate turn

Desired decision:

> stay safe or go collect them?

---

### B. Rock Gate

Purpose:

- create a readable steering test

Layout concept:

- rocks form two or three lanes
- one lane is wide and safe
- another is tighter but contains wild bison

Desired decision:

> easy line or higher-value line?

---

### C. Fence Choice

Purpose:

- make herd size matter strategically

Layout concept:

- a fence blocks the direct route
- edges leave a longer detour
- if the herd is already large enough, going straight is attractive
- optional wild bison near one side can help a small herd grow before the next fence

Desired decision:

> break through or steer around?

Do not dynamically rewrite the template based on herd size. The same physical situation should create different meaning depending on the player's current herd.

---

### D. River Reward

Purpose:

- use cohesion loss as a risk rather than a mandatory tax

Layout concept:

- one safer dry lane
- one river-crossing lane
- the river lane contains a meaningful recruit reward

Desired decision:

> preserve formation or accept disruption for growth?

Use multiple River rectangles if necessary to create a dry gap.

---

### E. Slalom

Purpose:

- stress delayed turn propagation and herd size

Layout concept:

- alternating rock positions require left-right corrections
- large herds should find the line visibly harder than small herds

Desired decision:

> how aggressively can I steer without shedding the rear of the herd?

Keep it readable. Do not turn it into pixel-perfect dodging.

---

### F. Compound Choice

Purpose:

- combine systems after the player understands them

Layout concept:

- first choice influences the next one
- example:
  - wild bison on risky side
  - then a fence shortly afterward
  - growing before the fence may make the direct route viable

Desired experience:

> my earlier route decision changed what I can do now.

Use this template only after some forward progression.

---

## 7. Encounter pacing

Do not spawn everything randomly at arbitrary coordinates.

Maintain a predictable sequence of encounter anchors along negative Y.

Recommended initial tuning:

- chunk spacing: roughly 450–650 px
- keep at least 2 upcoming encounter chunks spawned ahead
- do not place the first meaningful hazard directly on top of the starting area

The exact numbers must live in configuration.

Suggested config values:

~~~ts
encounterChunkSpacing
encounterSpawnAhead
encounterCleanupBehind
encounterInitialSafeDistance
~~~

Names may differ.

### First-run readability

The first encounters should be easier and more legible than later ones.

Recommended behavior:

- first encounter: Recruit Lure
- second encounter: Rock Gate
- afterward: choose from the eligible encounter pool

This provides a small amount of authored onboarding without introducing a tutorial screen.

---

## 8. Difficulty progression

Difficulty should increase with course progression, not elapsed time.

Use simple bands.

Example only:

### Band 0 — introduction

Approx. 0–400 forward px

- open
- recruitment-focused
- generous lanes

### Band 1 — basic decisions

Approx. 400–1200 px

- Recruit Lure
- Rock Gate
- simple Fence Choice

### Band 2 — combined systems

Approx. 1200–2400 px

- River Reward
- Slalom
- Fence Choice
- stronger route tradeoffs

### Band 3 — sustained run

2400+ px

- all templates eligible
- Compound Choice more common
- tighter but still readable layouts

Do not create unfair density by simply multiplying obstacle counts indefinitely.

The challenge should come from combinations and route choice, not visual clutter.

---

## 9. Template selection

Use weighted random selection from templates eligible for the current difficulty band.

Requirements:

- do not immediately repeat the exact same template
- preferably avoid the same template more than twice within a short rolling window
- deterministic seeded randomness is optional, not required for M2
- selection logic must be simple and inspectable

A small weighted bag / recent-history exclusion is enough.

Do not build a sophisticated procedural-generation framework.

---

## 10. Horizontal variation

The course should not look like every encounter is perfectly centered.

Each chunk may receive a small configurable X offset.

Example:

~~~ts
chunkCenterX = random between -180 and +180
~~~

However:

- keep the encounter comfortably reachable from the previous one
- do not force impossible cross-screen corrections
- do not let offsets accumulate indefinitely until the course drifts far away from the origin

Prefer independent bounded offsets around world X = 0 for this milestone.

---

## 11. Runtime spawning

Create a small director/system responsible for encounter lifecycle.

Suggested name:

~~~text
src/systems/EncounterDirector.ts
~~~

Responsibilities:

- know current course progress
- know next chunk Y
- select eligible encounter templates
- instantiate their wild bison / rocks / fences / rivers
- append spawned objects to the arrays used by GameScene / Herd
- remember which runtime objects belong to which encounter
- keep enough encounters ahead of the player
- clean up encounters far behind the player

GameScene should call the director, but should not itself contain all encounter-selection logic.

Avoid over-abstraction beyond that.

---

## 12. Cleanup

This milestone creates an endless-ish stream of objects, so old objects must be removed.

When an encounter is sufficiently behind the player:

- remove its rocks from the active rock array
- remove its fences from the active fence array
- remove its rivers from the active river array
- remove unrecruited wild bison that belong to that encounter
- destroy remaining Phaser graphics objects associated with those objects

Important:

- already recruited bison must **not** be deleted because their original encounter was cleaned up
- previously stranded active-history bison should not accidentally be removed as wild content
- a broken fence may already have destroyed its own graphics object; cleanup must tolerate that safely

Add small destroy helpers to obstacle classes if that makes cleanup clearer.

---

## 13. Spawn data ownership

The existing SpawnSystem currently contains one-time fixed arrays.

Refactor toward:

~~~text
src/systems/
  EncounterDirector.ts
  EncounterTemplates.ts
~~~

or an equivalently simple structure.

The old fixed arrays should no longer be the main gameplay source.

It is acceptable to leave tiny helper constructors in SpawnSystem, but the current finite world should be replaced by the director.

---

## 14. Route readability

The player must be able to understand choices before reaching them.

Therefore:

- spawn hazards far enough ahead to be visible
- do not create surprise rocks immediately under the camera
- leave clear negative space between lanes
- rewards should visually sit inside or beyond the risk they correspond to
- avoid layouts where the intended choice can only be understood after passing the decision point

The camera already has forward look-ahead; encounter spacing should take advantage of it.

---

## 15. Fairness constraints

Every generated encounter must satisfy:

1. At least one plausible route exists for a small herd.
2. The player is never required to already have 20+ bison to continue.
3. Breakable fences may create shortcuts, but not mandatory soft-locks.
4. A newly spawned obstacle must not overlap the leader or active herd.
5. Wild bison must not spawn inside rocks, fences, or fully inside hazardous geometry.
6. Consecutive chunks must not combine into an obviously impossible wall by accident.
7. Route widths must account for herd footprint, not just leader radius.

This milestone is about interesting choice, not surprise failure.

---

## 16. Existing mechanics that must remain intact

Preserve current behavior unless required for encounter compatibility:

- desktop steering
- mobile left/right hold steering
- herd-size turn penalty
- delayed turn propagation
- straggler loss
- re-recruiting stranded bison
- rock collisions
- fence break threshold
- river slowdown / weakened cohesion
- camera zoom
- camera look-ahead
- dust
- recruitment feedback
- impact feedback
- score HUD
- game-over screen
- retry

### Leader collision behavior

For M2, preserve the current rule:

- leader hits an unbreakable rock -> run ends
- leader hits a fence the herd cannot break -> run ends

This may be revisited later, but it is not part of this milestone.

---

## 17. Development controls

Keep existing herd-size test keys.

Add only lightweight encounter debug information if useful, for example:

- current course progress
- encounter index
- last template id
- number of active encounter chunks

Do not build a debug UI.

If convenient, add a dev key to force-spawn / cycle encounter templates, but this is optional.

---

## 18. Performance

The encounter system should remain lightweight on mobile browsers.

Requirements:

- only a few chunks exist ahead / behind at once
- old graphics and references are cleaned up
- no unbounded arrays
- no expensive full-world scans when avoidable
- do not create hundreds of obstacles merely to increase difficulty
- continue to support 100+ active bison reasonably

Gameplay simulation remains more important than decorative generation.

---

## 19. Manual evaluation

After implementation, test at minimum:

### Test A — continuous content

Play far beyond the old fixed river.

Check:

- new encounters keep appearing
- there is no long permanent empty stretch
- old objects disappear behind the player

### Test B — route choice

Play Recruit Lure / Rock Gate repeatedly.

Check:

- you can identify at least two meaningful options before committing
- the higher-reward option is visibly riskier

### Test C — herd-size meaning

Approach Fence Choice with:

- small herd
- 20+ herd

Check:

- the same encounter creates a different practical decision

### Test D — river tradeoff

Check:

- a dry route exists
- a river route offers a reason to take it
- river crossing can cause real formation risk

### Test E — large herd

Use 50–100 bison.

Check:

- Slalom is harder because of herd handling, not because gaps are impossible
- encounters remain readable
- cleanup / spawning does not create obvious frame instability

### Test F — long run

Play several minutes.

Check:

- arrays do not grow without bound
- graphics behind the player are removed
- encounter variety remains acceptable
- no impossible wall is produced

---

## 20. Acceptance criteria

v0.2 M2 is complete when:

- fixed finite obstacle placement is no longer the main gameplay structure
- hand-authored encounter templates exist
- at least 6 meaningfully different templates exist
- encounters spawn continuously ahead of the player
- encounters are selected based on forward progress / difficulty
- exact immediate repeats are prevented
- route choices repeatedly trade safety against reward or herd power
- old encounters are safely cleaned up
- recruited bison are never deleted by encounter cleanup
- existing herd / obstacle / feel systems still work
- a multi-minute run continues producing decisions
- performance remains acceptable at large herd sizes

---

## 21. Stop condition

**STOP after the Encounter / Route System works and has been manually tested.**

Do not implement MOMENTUM / STAMPEDE yet.

Do not add new obstacle categories yet.

Do not add final art yet.

The question at the end of M2 is:

> Does the game now create enough repeated decisions that simply surviving and growing the herd feels like a real run rather than a tech demo?
