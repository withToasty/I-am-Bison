# I AM BISON — v0.3 World Structure Specification (Biome Map)

## 1. Purpose

v0.2 proved the moment-to-moment loop: steer a growing, heavy herd, recruit
wild bison, and make route choices inside hand-authored encounter chunks
along a single forward corridor.

v0.3 turns that single corridor into a **world**: a sequence of distinct
biomes the player moves through, with real forks between them, a safe
detour hub (the ranch), and content gated by how far the herd has traveled.

> 「僕はバイソン」＝ 群れを率いて、どこまでも大移動するゲーム。終点はない。

This spec defines the world's shape. It does not touch the herd/steering/
recruit/loss systems, which are unchanged.

---

## 2. Core constraint: forward-only movement

The herd always moves forward (spec section 6) and there is no player
control over deceleration, braking, or reversing. This is not just a
mechanical detail - it's why cleanup-behind-the-player is safe, why
`courseProgress` is a simple scalar, and why the camera/look-ahead system
works the way it does. v0.3 must not break it.

So the biome map is **not** a free-roam 2D world the player can wander in
any direction. It is a **directed, acyclic sequence of biomes** ("segments")
joined by:

- **Forks** - a segment ends in two or more next-segment options; the
  player picks one by which side of the course they're on when they reach
  the fork, and the game never generates the unchosen side.
- **Spurs** - a bonus side-segment (the ranch) that peels off from a
  biome, and rejoins the main sequence at that same biome's normal
  continuation. Visiting it is a detour in *content*, not a detour in the
  movement model - the herd never turns around or reverses.

The user's diagram (`川 ⇄ 牧場`, `森林 ⇄ 道路`) is read as: **either
ordering is a valid path through the graph**, not literal backtracking
within one run. A single run only ever moves forward through the graph.

```
grassland
    |
   river --(spur)--> ranch --(rejoin)--> [continues as if river was taken]
    |
forest <---> road        (either order reachable, never both in one run)
    |
canyon
    |
snowfield
    |
   ???
    |
  (procedural remix, difficulty keeps climbing - no authored end)
```

## 3. Biome graph

A **biome** is a named, themed stretch of the world: its own encounter
template pool (existing `EncounterTemplate[]` shape, reused as-is) and its
own visual identity (ground texture tint, ambient obstacle palette).

```ts
interface BiomeNode {
  id: string;
  minTotalProgress: number; // cumulative course progress, not per-biome
  length: { min: number; max: number }; // how much courseProgress this biome lasts before its exit fork
  templates: EncounterTemplate[]; // this biome's own encounter pool (v0.2 shape, reused)
  groundTheme: GroundTheme; // tile color/tint, mottling palette
  exits: BiomeExit[]; // 1+ ways forward; 1 exit = no real choice, just a theme change
}

interface BiomeExit {
  toBiomeId: string;
  weight: number; // relative pick weight when the fork is rolled
  side: "left" | "right" | "either"; // which physical lane commits to this exit
}
```

Initial graph (matching the user's sketch):

| Biome       | Exits                                  |
|-------------|-----------------------------------------|
| grassland   | river (left), ranch-spur (right, detour)|
| river       | forest, road (fork)                     |
| ranch       | rejoins into river's own exit fork      |
| forest      | canyon                                  |
| road        | canyon                                  |
| canyon      | snowfield                               |
| snowfield   | beyond ("???")                          |
| beyond      | beyond (self-loop: procedural remix, see section 8) |

`ranch` is reachable only as a spur from `grassland`, not a normal node in
the main sequence - see section 6.

---

## 4. Segments (implementation unit)

A **segment** is one instantiated run through a biome: a contiguous
stretch of `courseProgress` during which `EncounterDirector` draws only
from that biome's template pool, exactly like today's single global pool.

Nothing about chunk generation, spacing, or cleanup changes *inside* a
segment - v0.2's `EncounterDirector` logic (fillAhead, pickTemplate,
cleanupBehind, anchor meander) is reused per-segment unmodified. What's new
is what happens at a segment's end.

---

## 5. Forks

A fork is not free-form branching geometry - it's a **committed chunk**,
authored like any encounter template, whose job is to visually present 2+
onward paths and then let the player's own position decide which biome
continues.

Mechanically:

1. As a biome segment approaches its rolled `length`, the director spawns
   a **fork chunk** instead of a normal encounter: the ground visibly
   splits (e.g. a rock spine or tree line down the middle, themed to blend
   the current biome into each destination biome just beyond it) into a
   left lane and a right lane, both clearly passable, both visibly
   themed toward their destination.
2. Normal encounter generation pauses (no new chunks spawn) for a short
   `forkDecisionWindow` of `courseProgress` after the fork chunk, giving
   the player room to commit to a side without being crowded.
3. Once the leader's X position clears a `forkCommitThreshold` to one
   side, the director sets `currentBiome` to that exit's `toBiomeId` and
   resumes normal generation - now drawing from the new biome's pool and
   ground theme.
4. If the player is still near dead-center when `forkDecisionWindow`
   elapses, default to the exit whichever side they've drifted closer to;
   if exactly centered (rare), pick by exit weight.

Because generation is already lazy (only ever spawns what's
`encounterSpawnAhead` in front of the player - see v0.2 M2), the unchosen
branch's content is simply never generated. There's no wasted work and no
need to render two parallel worlds.

## 6. The ranch (detour spur)

The ranch is `grassland`'s optional right-hand exit at its first fork,
flagged as a **spur** rather than a normal exit:

- Its own segment is short and deliberately generous: guaranteed multiple
  wild-bison groups, no rocks/fences/rivers, functionally the safest
  ground in the game.
- It has exactly one exit, which does not point at a new biome - it
  **rejoins** whatever `grassland`'s non-spur exit was already resolved to
  (i.e. the river fork). Taking the ranch costs the player some lateral
  distance and time, not progress toward the rest of the graph.
- This is the general pattern for any future hub/detour: a spur is a
  segment whose exit is `{ rejoin: true }` instead of `{ toBiomeId }`.

This gives the "牧場寄って仲間増やすか / いや先へ行こう" decision the user
described, without introducing backtracking.

## 7. Biome visual identity

Each biome swaps a small palette, not new rendering code:

```ts
interface GroundTheme {
  backgroundColor: number;
  backgroundLineColor: number;
  mottlePalette: number[]; // 2-3 tints, reusing GameScene's existing patch logic
}
```

`GameScene.generateGroundTexture()` becomes theme-parameterized (one
texture per biome, generated on first use and cached by biome id - same
technique already used for `ground`/`dust`/`debris`/`river-flow`). Obstacle
classes (Rock/Fence/River) don't need per-biome variants for v0.3 - only
the ground and ambient palette shift; new obstacle *types* per biome
(trees in forest, ice in snowfield) are a later milestone, not this one.

## 8. Progression gating and discoveries

Two independent gates, both keyed off cumulative `courseProgress` (already
tracked) rather than per-biome position, so they read as "how far the herd
has traveled overall":

- **Distance-gated content**: an encounter template (or a rare one-off
  "discovery" object) can set `minTotalProgress` far beyond where its
  biome normally starts, so it only appears deep into a long run - e.g. a
  rare animal that only spawns 10km+ in, regardless of which biome that
  happens to fall in.
- **Herd-size-gated content**: reuse the existing fence-break-by-size
  mechanic's pattern for a new obstacle variant (e.g. a "massive fence" or
  rock formation) whose passable gap requires `herdSize >= N`, giving
  the "50頭以上いないと突破できない場所" moments.

"発見" (discoveries) are simply encounter templates or standalone objects
flagged `discovery: true`; touching/passing one increments a `discoveries`
counter for the end-of-run summary (section 9) once per run, independent
of the destroyed-obstacle counter.

## 9. End-of-run summary (extends existing GameOverScene)

The existing fields (distance, max herd, destroyed) stay. Add:

```
今回の大移動
移動距離     8.7 km
最大群れ     54頭
到達群れ     31頭
発見         3
破壊         27
新記録       最長移動距離！
```

`到達群れ` (herd size at the moment of death) is new and distinct from
`最大群れ`. "新記録" is a best-of-session/local-storage comparison against
prior runs' `courseProgress` - a small addition to `GameOverScene`, no new
systems.

---

## 10. The tail ("???" / "beyond")

Once the player passes the last authored biome (snowfield), enter a
`beyond` biome that:

- Draws its template pool from a remix of all previous biomes' templates
  (still no new authored content required),
- Scales density/difficulty continuously with `courseProgress` past that
  point (reuse the existing "no fixed ending, difficulty from distance"
  principle - spec section 14),
- Self-loops (`beyond -> beyond`) so the graph never runs out of "next
  biome," matching "終点はない."

This keeps "no authored end" true without requiring infinite hand-authored
content.

## 11. Suggested implementation milestones

### M-B1 - Biome data model + single fork

- `BiomeNode`/`BiomeExit` types; hardcode just `grassland -> {river, forest}`
  (two biomes, one real fork, no ranch yet).
- `EncounterDirector` gains `currentBiome` state and switches template pool
  + ground theme on fork resolution.
- Done when: a player can visibly steer left or right at the fork and see
  the encounter pool/ground theme change afterward.

### M-B2 - Full authored graph

- Add remaining nodes through `snowfield`, each with a starter template
  pool (can reuse existing 9 templates re-skinned before bespoke per-biome
  ones are authored).
- Done when: a long run visibly passes through every biome in some order.

### M-B3 - Ranch spur

- Spur segment type, rejoin-exit resolution.
- Done when: taking the ranch does not skip or duplicate the segment the
  player would otherwise have reached.

### M-B4 - Discoveries, herd-size gates, `beyond`

- `discovery` flag, herd-size-gated obstacle variant, `beyond` remix biome.
- Done when: all fields in section 9's summary populate correctly across a
  multi-kilometer run.

### M-B5 - GameOverScene summary + best-run record

- New fields, local-storage best-distance comparison.

**STOP after M-B2 for a first manual playtest**, same discipline as v0.2:
confirm the fork/theme-switch actually reads as "a different place," not
just a recolored version of the same corridor, before building the ranch
and gating systems on top of it.

---

## 12. Non-goals for v0.3

- Free 2D roaming / backtracking / turning the herd around.
- New per-biome obstacle types (forest trees, snowfield ice) - reuse
  rock/fence/river with new themes/positions only.
- Real predators/enemies/vehicles - this spec is world structure only; the
  "what makes the herd decline" attrition design is a separate spec.
- Persistent server-side records, accounts, or leaderboards - "新記録" is
  local-storage only.
- Minimap/UI showing the graph to the player - the world should be
  discovered by playing, not read off a menu.

---

## 13. Open questions

- Exact fork geometry (how wide the visual split needs to be at the
  player's current camera zoom/look-ahead to read as two lanes rather than
  one wide obstacle) needs a manual pass once M-B1 is playable - this spec
  intentionally leaves `forkCommitThreshold`/`forkDecisionWindow` as tuning
  values rather than fixed numbers.
- Whether `beyond`'s remix should ever introduce a genuinely new template
  rather than only recombining existing ones is deferred until M-B4.
