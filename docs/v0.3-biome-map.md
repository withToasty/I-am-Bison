# I AM BISON — v0.3 World Structure Specification (Biome Map)

> **Revision 2.** The original version of this doc modeled the world as a
> one-way graph of biomes (fork here, rejoin there), built around the
> assumption that the herd can never turn back. That assumption turned out
> to be false: heading has no limit today, so a player can already steer a
> full U-turn. Rather than patch that out, this revision embraces free
> movement in any direction and redesigns the world to match. See git
> history for the superseded graph version.

## 1. Purpose

The herd should be free to go anywhere - including back the way it came -
without the world falling apart when it does. This doc describes a world
that doesn't need to remember "which way is forward": every point in space
has content that's computed from its coordinates, so revisiting a place
regenerates what was there instead of finding it deleted.

Biomes blend into each other gradually (grassland fading into forest, never
a hard line), matching the user's "グラデーションで変える" direction, and
also happen to solve the technical problem cleanly - see section 3.

---

## 2. The core idea, in plain terms

Today, content is generated in a line: a little bit is created just ahead
of the player, and it's destroyed once they've passed it, because the game
assumed they'd never come back. That's why a U-turn currently leads to
empty grass - the world behind the player has been deleted, not just
hidden.

The fix: stop treating "generate" and "remember" as the same step.

- **Generating** content for a location becomes a pure calculation: feed in
  a coordinate, get back the same rocks/fences/wild bison/river every time.
  Like a formula, not a memory.
- **Deleting** stays purely about performance - it only destroys the
  on-screen graphics for places currently far from the player. It never
  discards the *ability* to reproduce that place if they return, because
  reproducing it is just running the same formula again.
- A small amount of real memory is still needed for the handful of things
  that must *not* regenerate identically forever - a wild bison group the
  player already recruited shouldn't reappear. That's a short list of "this
  one thing changed" notes (section 7), not the whole world.

This is the same trick as a lot of open-world/roguelike games: the world
isn't a big saved file, it's a function of coordinates plus a short diary
of exceptions.

## 3. Biome field (the gradient)

Every world coordinate has a **biome blend** - not one biome, several,
each with a weight that sums to 1. Two ideas combine to produce it:

### 3.1 Rings by distance from spawn

Reusing distance-from-spawn (already how the DISTANCE score works today),
each biome owns a radius band. Bands overlap, and a coordinate's weight for
a biome fades in/out smoothly across the overlap instead of snapping:

```
radius from spawn (px)
0 ─────── 1400 ──────── 2600 ──────── 4200 ──────── 6500 ────────→
[  grassland  ]
            [  forest / road  ]
                          [    canyon    ]
                                        [   snowfield   ]
                                                       [    beyond    ]
```

A coordinate at radius 1900 might be 60% forest / 40% grassland - its
ground tint blends, and its encounter pool draws from both biomes'
templates in that proportion (section 6).

This means: standing still and walking in a slow circle keeps the player
in roughly the same biome band forever (matching "広めのエリアを自由に動
ける" - free lateral movement without being forced onward). Walking
outward in any direction is what advances biome (and difficulty).

### 3.2 Angular noise, so rings aren't perfect circles

A smooth noise function of angle (section 3.4) perturbs each band's radius
by up to ±15%, so the boundary between grassland and forest is a wobbly
coastline, not a perfect circle. This is cosmetic only - it doesn't change
which biomes exist, just where their edges fall.

### 3.3 Rivers as a cross-cutting feature, not a ring

A river isn't a distance band - real rivers cut across terrain. Model it
as its own independent noise channel: wherever that channel's value
exceeds a threshold, a river influence is added to the blend regardless of
which ring the coordinate is in, so a river can wind through grassland,
then forest, same as the user's diagram implies (`川` sits beside multiple
biomes, not inside one).

### 3.4 The noise function itself

No external library - value noise is a small, self-contained function:
hash the four integer corners of whatever grid cell a coordinate falls in
to pseudo-random values, then bilinearly interpolate between them. A
handful of octaves at different scales (large-scale for ring wobble,
smaller-scale for river winding) is enough. This keeps the "no new
dependencies" property the project has had since M0.

```ts
function valueNoise2D(x: number, y: number, seed: number): number; // -1..1
```

## 4. Landmarks (the ranch, and similar)

Some places should always be in the same spot, not distributed by a field
- so the player can actually navigate back to them on purpose. The ranch
is one of these: a fixed world coordinate (chosen once, e.g. 900px east of
spawn), with its own guaranteed-safe, recruit-rich content, independent of
whatever the biome field says about that location.

A landmark is simply: `{ id, x, y, radius, content }` - when the player is
within `radius` of `(x, y)`, that landmark's content overrides the normal
field-driven generation for that area. Canyon monuments, the first
"discovery" objects, and similar one-of-a-kind places all use this same
mechanism. This directly gives "なんだあれ？ちょっと見に行こう" - a
landmark can be visible from far off (tall silhouette, distinct color) and
worth a deliberate detour to reach.

## 5. Content generation (reuses v0.2's template system almost unchanged)

The existing `EncounterTemplate` shape (wild groups, rocks, fences, rivers,
authored relative to a local anchor) is still exactly how content is
authored. What changes is *how a template gets picked and placed*:

- The world is divided into a grid of cells (suggest 600×600px, close to
  today's chunk spacing).
- Each cell has a **stable seed** derived from its integer coordinates
  (e.g. a hash of `cellX, cellY, runSeed`), which drives every random
  choice about that cell's content, so the same cell always produces the
  same result.
- When a cell needs content, compute its biome blend (section 3), then use
  the cell's seed to weighted-pick one template from the combined pool of
  every biome present in that blend (a cell that's 60% forest / 40%
  grassland draws from forest templates 60% of the time, grassland 40%).
- The template is instantiated at the cell's center, **rotated by a random
  angle** (also from the cell's seed) before placing its local offsets.
  Templates were authored assuming "reward is further from the start
  lane," which no longer has one fixed compass direction - rotating keeps
  that framing valid regardless of which way the player approaches from.

No new templates are required to start (the existing 9 keep working); new
per-biome templates (forest-specific, canyon-specific...) are additive
later work, not a prerequisite.

## 6. Streaming: what's loaded, what's remembered

Every frame (or on a short timer), compute which cells fall within a
`loadRadius` of the player (suggest a 5×5 cell window) and which don't:

- A cell entering range: compute its content (section 5) if not already
  computed this run, apply any diff (section 7), instantiate Phaser
  objects.
- A cell leaving range: destroy its Phaser objects. Its content is *not*
  forgotten - only its on-screen representation is. If the player returns,
  the same generation function runs again and produces the same layout.

This is the same idea as v0.2's `EncounterDirector`, just indexed by 2D
cell coordinate instead of a 1D forward frontier, and "cleanup" now means
"unload," never "delete forever."

---

## 7. The diff: what actually needs memory

A small, run-scoped record of exceptions to "just recompute it":

```ts
interface WorldDiff {
  recruitedWildGroups: Set<string>; // cellKey + group index, once recruited, never regenerate
  brokenFences: Set<string>; // cellKey + fence index, stays broken
  visitedLandmarks: Set<string>; // for "発見" scoring (section 9 of the old graph doc, unchanged)
}
```

This is tiny relative to full graphics objects - a few IDs per interaction,
not per cell. It only grows with how much the player actually *does*
(recruits, breaks, discovers), not with how far they wander, and it's
cleared on retry like every other run-scoped state today.

## 8. Difficulty and scoring

Unchanged in spirit, re-based on radius instead of forward-only progress:

- Encounter density/danger scales with distance-from-spawn (already
  computed for the DISTANCE score) instead of `courseProgress` - a
  concept that no longer exists, since there's no single forward axis.
- DISTANCE, MAX HERD, DESTROYED, 発見 all continue to work exactly as
  today (DISTANCE was already straight-line displacement from spawn - see
  `GameScene`'s existing comment - so this is one less thing to change,
  not more).
- Herd-size gates (50頭以上でしか通れない場所) can be landmark or
  high-radius-band content unchanged from the original plan.

---

## 9. What this replaces from v0.2 M2

- `EncounterDirector`'s frontier/spacing/cleanup-behind logic is replaced
  by the cell loader (section 6). The anchor-meander logic (drifting X per
  chunk) is no longer needed - free 2D movement makes it moot.
- `EncounterTemplates.ts` and its 9 templates carry over unchanged in
  shape; they're re-tagged by which biome(s) they belong to.
- `minProgress`/`maxProgress` per template are replaced by biome tagging
  (a template belongs to grassland, forest, etc. - eligibility comes from
  the biome blend, not a progress number).
- Score/HUD/game-over logic is unchanged (section 8).

## 10. Data model sketch

```ts
interface Biome {
  id: string;
  ringMin: number; // px from spawn where this biome starts fading in
  ringMax: number; // px from spawn where it's fully faded out
  templates: EncounterTemplate[]; // existing v0.2 shape
  groundTheme: GroundTheme;
}

interface Landmark {
  id: string;
  x: number;
  y: number;
  radius: number;
  content: EncounterTemplate; // reuses the same authoring shape
}

interface CellContent {
  cellX: number;
  cellY: number;
  templateId: string;
  rotation: number;
  // instantiated Rock/Fence/River/WildBison objects, present only while loaded
}
```

## 11. Suggested implementation milestones

### M-G1 - Deterministic single-biome grid

- Cell grid + seeded generation for grassland only, no rings yet.
- Load/unload window replaces `EncounterDirector`'s frontier logic.
- Done when: walking in a large circle, or straight out and back,
  reproduces identical layouts each pass, with no crashes and no memory
  growth from revisiting the same cells repeatedly.

### M-G2 - Ring blending

- Add remaining biomes as ring bands with smooth blend weights; ground
  theme interpolates visually across a boundary.
- Done when: walking straight outward visibly and gradually shifts ground
  color/obstacle mix, with no hard seam.

### M-G3 - Rivers as a cross-cutting noise channel, angular wobble on rings

- Done when: a river is found winding across more than one biome band in
  a single run.

### M-G4 - Landmarks (ranch first)

- Fixed-coordinate override content; visited-landmark tracking for 発見.
- Done when: the ranch is reliably at the same place across retries, and
  visiting it doesn't disturb generation nearby afterward.

### M-G5 - Diff persistence correctness pass

- Confirm recruited groups and broken fences never regenerate after
  unload/reload across a long, backtracking-heavy manual playtest.

**STOP after M-G2 for a manual playtest**, same discipline as before:
confirm the gradient actually reads as "the world is changing," and that
free backtracking feels good rather than aimless, before building
landmarks and diff-correctness on top.

---

## 12. Non-goals for v0.3

- Persistent world save between runs - the diff and generated cells are
  run-scoped only; a retry starts clean.
- New per-biome obstacle types (forest trees, snowfield ice) - reuse
  rock/fence/river with new themes/positions only, same as v1's non-goal.
- A minimap or any UI exposing the field/grid to the player.
- Predators/enemies/attrition mechanics - separate spec, as before.

---

## 13. Open questions

- Cell size and load-radius are tuning values, not fixed here - depends on
  how large a template needs to breathe and how many cells are affordable
  to keep loaded on mobile.
- Whether ring boundaries should also drift slowly with distance in a
  fixed compass direction (so "north" trends toward snow faster than
  other directions, giving the world a *little* asymmetry) is worth a
  manual pass after M-G2, not decided here.
- Upper bound on `WorldDiff` size for an extremely long single run is
  unlikely to matter in practice (a run ending in death is bounded by how
  long a player survives) but isn't formally capped in this spec.
